**Blocking:**

1. **Criterion 4.** `packages/guard/src/guard.ts:236`: `result.outcome === 'replayed' ? 'ok'` reports an `outcome_unknown` original as completed to `@ark/sdk`/Control, because `'ok'` is in `COMPLETED_OUTCOMES` (`packages/core/src/ingest/evidence.ts:41`). To earn the point back, derive a replay's evidence outcome from `result.executionStatus`: only `completed` may become `'ok'`. `outcome_unknown`, `failed` and an in-flight `attempted` must map to a non-completed outcome (e.g. `'error'`, or `'blocked'`, since this attempt executed nothing). Add a test next to `guard.test.ts:258` or `:467` asserting that the replay of a crashed call emits an outcome outside `COMPLETED_OUTCOMES`. The existing assertion at `guard.test.ts:474` covers only the replay of a completed call.

**Non-blocking:**

- Decide whether a replay should emit `'ok'` even when the original completed. This attempt executed nothing, and `emit` sends a second `mcp`/`tool` row with a fresh `evidenceRef` (the replay's decision id). Control may count one refund as two completed operations. Using the original's id as `evidenceRef`, or emitting replays as `blocked`, would avoid the double count. This is a design choice, not a defect in this round.
- The receipt store calls (`store.record`/`claim`/`finish`/`get`, `guard.ts:374,408,423,440`) have no timeout, while context, policy and handler each have one. With a local file this does not matter. With `openActionReceiptStore(url, authToken)` pointed at remote libSQL, a hung store hangs the guarded call. If `finish` hangs, it does so *after* money moved. This follows the repo's existing libSQL usage, so it is not scored, but consider a `receiptsMs` timeout that fails closed before the claim and records `receipt_update_failed` after it.
- Deviation 4 (digest recomputed at the claim's `now`) is sound and tested: replay `guard.test.ts:209`, conflict on amount, order and agent `:224-245`. It depends on `decideAction`'s `requestDigest` ignoring the policy list and on the kernel's normalization staying stable. A future kernel change to normalization would turn old replays into `idempotency_conflict`. That fails closed, but a comment at `guard.ts:217` saying so would help the next kernel author.
- Deviation 6 (receipt id = decision id): two identical refunds with different keys in the same millisecond are blocked as `receipt_conflict` (`guard.test.ts:272`). This fails closed and is accepted. If real usage hits it, a per-call nonce in the receipt id would remove it without changing the decision id.
- Deviation 1: when PR-1 lands, the three `action_receipts` statements in `packages/db/src/sql.ts:144-160` must move into a numbered migration, as EVIDENCE.md says. Track this so it is not lost.
- Deviation 8 (telemetry via `evidence()` rather than `action()`) is justified: action rows would be counted as actions taken for blocked attempts. `approvedBy: null` is hard-coded and tested (`guard.test.ts:473`).
- Privacy: no column can hold raw arguments, the note, a prompt or the raw key (`action-receipts.test.ts:52`, `guard.test.ts:425`). `principal` and `resource_id` are caller-chosen identifiers and could hold an email if a caller maps one. EVIDENCE.md declares this. A one-line warning on `TrustedContext.principal` and `GuardedAction.toRequest` would put it where integrators will read it.
- `before.txt` header says `2026-10-19T07:11:47Z`, while `captures.tsv` records `07:11:32Z` for the same capture. The commit and `dirty=0` agree, so the comparison holds. The two stamps should still come from one clock read.
- `demo/run.ts:69` reads `store.list` directly from the entrypoint for its summary count. This is acceptable for a demo composition root, but it is the one place an edge reads the adapter.
- The security review (`agents/security-reviewer.md`) is still required by the spec's Risk section before ship. This round does not replace it.
